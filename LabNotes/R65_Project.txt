== Definition of VIEW: ==

R65 VIEW (Pager / Browse Tool) — Design Session (Yesterday)

Goal
Definition of a small, safe, read-only file inspection tool (“VIEW”) for the R65 system.
The tool replaces the current inspection workflow (export → edit → import) with a controlled in-system browsing capability.

Motivation
During inspection it is easy to drift into editing, often leading to unnecessary work.
VIEW is therefore designed as:

* strictly read-only
* no editing capability
* no write-back
* no interaction with the edit/import workflow

It should act as a safe inspection window.

Basic Design Decisions

* entire file is read into memory before browsing begins
* no partial buffering (Version 1)
* clear separation between load phase and browse phase

Startup sequence:

1. read file line by line
2. allocate heap space per line (cpnt)
3. store pointer in line table
4. store line length
5. check free memory continuously
6. stop if memory below safety threshold

Only after successful load:

* clear screen
* disable scrolling
* enter browse mode

Memory Strategy

* one heap allocation per line
* pointer table limits total number of lines (~500 expected)
* minimum free memory reserve: 512 bytes

This ensures stable operation after loading.

Internal Structures

* lineptr[] : array of cpnt (text lines)
* linelen[] : array of integer (line lengths)
* nlines    : total number of lines
* topline   : first visible line

Search state:

* search string
* current match position
* highlight information

Display Concept (Initial Version)

* status line (inverse video)
* 15 lines of text below
* 48 characters per line (initial assumption)

Wraparound Discussion
Line wrapping was analyzed in detail:

* wrapping creates variable screen rows per line
* paging becomes undefined
* navigation becomes complex
* search positioning becomes difficult

Options considered:

* dynamic wrapping during display
* pre-expanded buffer
* additional metadata

Conclusion:

* wrapping is undesirable for this tool
* it adds complexity without sufficient benefit

Performance Considerations

* avoid repeated strlen during display
* store linelen[] at load time
* use write(string) for output
* clear-to-end-of-line after each row

Goal: fast and simple display.

Navigation Model

* topline defines first visible file line
* screen is filled from that line downward

Keys:

* up/down: ±1 line
* left/right: ±1 page (≈15 lines)
* shift left/right: ±5 pages
* q / ESC: quit
* / or f: search
* n: next occurrence
* h / ?: help

Search Concept

* simple forward substring search
* wraps at end of file
* match highlighted (inverse video)
* new search clears previous highlight
* match positioned near middle of screen

UI Considerations

* minimal command set
* no modes except temporary search input
* status line shows position, filename, search field
* focus on clarity and predictability

Preliminary Conclusion
The design is:

* simple
* robust
* memory-efficient
* strictly read-only

Main open issue identified: handling of line wrapping, leading to further refinement in the next session.

Remark
Avoiding complexity is intentional. VIEW should remain a small, reliable inspection tool and not evolve into an editor.

VIEW design update

The wraparound problem is eliminated by using the 56-character display mode already known from PEDIT. Historically, the standard console showed 16 lines of 48 characters with hardware scrolling, while PEDIT used a squeezed 56-character mode with software scrolling. This mode is also available in the emulator and is suitable for VIEW.

Therefore VIEW will display:

1 status line
15 text lines
56 characters per line

Each source line corresponds to exactly one display line. This makes paging simple and exact.

Lines longer than 56 characters are truncated while filling the internal line buffer. In normal R65 usage this should almost never occur, since INPUT, EDIT and PEDIT all produce lines of at most 56 characters.

The cursor should normally be hidden, for example by placing it off-screen on line 17. It is only shown when entering a search string in the status line.

This is a much cleaner design than wraparound and fits the intended purpose of VIEW very well.

This looks like a very solid starting point for implementation.

With the current standard STRLIB allocation size of 65 bytes per line, VIEW can hold about 423 lines with the present code size, leaving about 1493 bytes free. Since VIEW only reads lines once and never modifies them afterwards, a private exact-length allocator for line storage becomes attractive. This would likely increase file capacity substantially, perhaps close to a factor of two. The disadvantage is that such strings would no longer be standard STRLIB objects and would have no built-in range checking. However, because VIEW treats them as immutable after loading, this may be an acceptable local optimization.

R65 VIEW — Status Line Input Field (Find)

Purpose
Minimal editor for entering a case-sensitive search string on the status line.

General

* invoked by `/` or `f`
* existing search string is presented for editing
* editing is append-only (cursor always at end)
* ENTER accepts
* ESC cancels (previous string unchanged)

Storage

* `findstr: cpnt`
* max length: `FINDMAX` (currently 28)
* allocated once with `FINDMAX+1` bytes
* ENDMARK always maintained

Display

* status line = row 0
* normal mode: full status line in inverse video
* edit mode: input field in normal video
* one character to the right remains inverse video

Cursor Behavior

* cursor only visible during editing
* always positioned at end of string
* no movement inside string
* LEFT/RIGHT ignored in edit mode

Important hardware rule:
Cursor becomes visible only after writing a character.
Therefore every cursor move must be followed by at least one write.

Editing

* printable char:

  * if len < FINDMAX → append
  * if len = FINDMAX → ignore
* BACKSPACE:

  * if len > 0 → remove last char
* no insert mode, no overwrite mode
* no shifting
* no HOME/END

Field Full

* cursor remains on last character
* further input ignored
* no visual change

Exit

* ENTER: accept string
* ESC: restore previous string
* after exit: redraw full status line in inverse video (visual confirmation)

Design Principles

* minimal code
* deterministic behavior
* no hidden state
* no dependency on STRLIB
* no interference with navigation keys

R65 VIEW — Cursor and Indexing Conventions

Cursor handling

Originally, setting the cursor position only changed the software cursor variables. The hardware cursor became visible at the new position only after an actual character write. This complicates status-line editing, because cursor movement and display output are no longer independent.

For VIEW, `movecursor(x,y)` is therefore redefined so that it immediately updates the hardware cursor as well. No following write is needed to make the cursor appear at the new position.

This has two advantages:

* cursor logic becomes simple and predictable
* the cursor can be hidden by moving it to an off-screen line

In VIEW, the visible screen lines are:

* line 0 = status line
* lines 1..15 = text area

The cursor can therefore be hidden by moving it to line 16.

This is the preferred design for VIEW.

Indexing conventions

The program uses both 0-based and 1-based indexing. This is intentional, but must be clearly separated.

1. Screen coordinates

Screen line numbers are 0-based:

* row 0 = status line
* rows 1..15 = text lines
* row 16 = hidden cursor position

Column numbers are also 0-based.

Thus `movecursor(0,0)` means start of status line.

2. Stored line buffer

The internal line pointer table is 0-based:

* `lineptr[0]` = first stored file line
* `lineptr[nlines-1]` = last stored file line

This follows the normal Pascal array model used in the program.

3. Logical file line numbers

Logical line numbers used for browsing and searching are 1-based:

* first file line = 1
* last file line = `nlines`

This is more natural for status display and search results.

Therefore the mapping is:

* logical line `i` corresponds to `lineptr[i-1]`

4. String indexing

Characters inside a `cpnt` string are 0-based:

* first character = `s[0]`
* end mark at `s[len]`

This follows the normal string handling convention already used elsewhere in the system.

Summary

The indexing rules are therefore:

* screen rows/columns: 0-based
* characters in strings: 0-based
* line buffer table: 0-based
* logical file line numbers: 1-based

Rule of thumb

Use 1-based values only where the user sees “line numbers” as logical file lines.

Use 0-based values everywhere that refers to:

* arrays
* string characters
* screen positions
* hardware/display coordinates

This gives a clean and consistent model.

R65 VIEW — Search Definition

Search routine is called `findtext`.

Search state consists of:

* current search string
* flag whether a match is currently active
* current match line and position

Behavior of first search (`searchfirst`):

* if no match is currently active, search starts at top of file (line 1, position 1)
* if a match is already active, search starts at that current match position
* this remains true even if the search string has been changed

This matches the behavior of modern editors: a new search starts from the current search position, not automatically from top, unless no current search position exists.

If a match is found:

* current match state is updated
* the page is repositioned so the match is shown near the middle
* the match is highlighted

If no match is found:

* current match remains unchanged
* status line may indicate “not found”

Behavior of next search (`n`):

* search continues with the same search string
* starts immediately after the current match
* wraps around at end of file

== VNC Keyboard Issue on macOS: ==

Date: 2026-04-03
Topic: Control + Arrow keys not switching Spaces when using VNC Viewer on macOS

Problem:
While running VNC Viewer in full screen on a dedicated Space, the key combination Ctrl + Left/Right Arrow stopped working for switching macOS Spaces. Instead, the keys were captured by the VNC session.

Observation:
The issue appeared unexpectedly after the setup had previously been working correctly. The same configuration had allowed macOS to retain control over Space switching.

Root Cause:
A new VNC connection profile was being used. In this profile, the setting:
	Pass special keys directly to VNC server? (or equivalent)

was enabled, causing VNC Viewer to capture control key combinations before macOS could process them.

Solution:
Adjusted the VNC connection settings:
	* Disabled: Pass special keys directly to VNC server
	* Ensured no full keyboard capture mode was active

After this change, macOS regained priority over:
	* Ctrl + Left Arrow
	* Ctrl + Right Arrow

and Space switching worked as expected.

Result:
* VNC runs in its own full-screen Space
* macOS Space navigation works reliably
* Emulator input (Option + Arrow) remains unaffected

Conclusion:
VNC keyboard handling is profile-dependent. When encountering unexpected key behavior, always verify the active connection profile and its keyboard settings.
